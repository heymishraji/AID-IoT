Build the whole site end to end before showing the CEO (technical, non-designer, time-poor); do not
ask the CEO intermittent questions. Log every decision in `docs/DECISIONS.md`; end every deliverable
with "next steps" and why each step is the right one. Generic / category-default design was rejected
("navy + orange glow + device on a sweep + bento") — the user wants modern, motion-led, 3D/scroll
storytelling with a templatised component system.

**Why:** the user gets clearer feedback from a working thing than from abstract questions, and wants
the project portable and agile.

**How to apply:** prefer committed, distinctive directions over safe ones; always propose next steps
with reasons; keep docs current and small. See [[aid-iot-project-home]].

Added 2026-10-30:
- Deliver a round end to end before review; the owner does not want mid-way checkpoints ("complete this end to end, then I will review").
- Research first, then design: for identity work (e.g. the logo), write the principles and a checklist before drawing variations, and show options in use (real screens, real touchpoint mockups), not as swatches or isolated marks.
- Every visual deliverable needs light and dark mode.
- The owner rejected new-logo routes; keep and modernise the current AID mark.
